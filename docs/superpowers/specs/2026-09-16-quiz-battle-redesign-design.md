# 퀴즈 배틀 — 리디자인 · 이미지 문제 · 문제별 순위

작성일 2026-09-16 · 대상 저장소 `nanjungj/quiz-battle`

## 1. 배경과 목표

현재 퀴즈 배틀은 다크 칠판 + 크레용 손글씨(Gaegu) 테마로 동작 중이다. 워크숍에서 실제로 써 본 뒤
세 가지 요구가 나왔다.

1. **디자인** — 교육생 폰과 강사 대형 스크린 모두 "심플하지만 꽉 찬" 화면. 친근하고 세련되게,
   색은 3~5가지, 퀴즈앤과 비슷한 톤.
2. **이미지 문제** — 그림·사진을 보고 푸는 문제가 필요하다.
3. **순위** — 문제마다의 순위(빨리 맞힌 순)와 최종 순위를 모두 볼 수 있어야 하고,
   최종 1·2·3등은 대형 스크린에, 나머지 순위는 강사만, 개인 순위는 각자 폰에서.

시각 시안은 별도 목업으로 확정했다: https://claude.ai/artifact/MoWRacj5YRYZjTzezFvMzf

## 2. 범위

**포함**

- 전체 스타일 교체(라이트 테마, 새 팔레트·폰트·레이아웃)
- 문제에 이미지 첨부 — 편집기에서 끌어다 놓기, 브라우저에서 압축해 Realtime Database에 저장
- 문제별 순위(빨리 맞힌 순) — 강사 스크린과 교육생 폰
- 최종 결과 분리 — 대형 스크린은 1·2·3등만, 전체 순위는 강사 전용 별도 창
- 개인 최종 결과 화면(등수·점수·맞힌 개수)
- 편집기 개선 — 문항 카드 접기, 순서 이동, 복제, 정답을 동그라미 체크로
- 전체 순위 CSV 내보내기

**제외 (이번에 하지 않음)**

- 팀전, 이미지 외 문제 유형 추가, 문제별 제한시간 개별 설정
- DB 보안 규칙 강화(점수 위조 방지). 워크숍 용도라 공개 규칙을 유지한다.
- 배경음악 변경 — 현재 `js/music.js` 그대로 둔다.

(점수, 걸린 시간, 순위)은 `font-variant-numeric: tabular-nums`.

### 레이아웃 규칙

- 교육생(폰): 보기 버튼이 가로를 꽉 채우고 남은 세로를 균등 분할한다. 최소 높이 64px.
- 강사(대형 스크린): `body.admin`의 확대 규칙을 유지하되 값을 새 스케일에 맞게 다시 잡는다.
- 이미지가 있는 문제는 레이아웃이 자동으로 바뀐다 — 폰은 이미지를 문제와 보기 사이에 두고
  보기를 한 단계 컴팩트하게, 대형 스크린은 좌우 2단(왼쪽 이미지, 오른쪽 문제+보기 세로 배치).

## 4. 데이터 모델 변경

문제 객체에 `image` 필드를 **선택적으로** 추가한다. 이미지 데이터 자체는 넣지 않고 참조만 넣는다.

```js
{
  type: 'mc' | 'ox' | 'short',
  text: '...',
  image: { id: 'k3f9d2', w: 1280, h: 720 },   // 없을 수 있음
  choices: [...], answer: ..., accepted: [...], double: false
}
```

`image`가 없는 기존 퀴즈는 그대로 동작한다(하위 호환).
`w`/`h`는 이미지가 도착하기 전에 자리를 미리 잡아 화면이 덜컥거리지 않게 하는 용도다.

이미지 실물은 **퀴즈와 분리된 경로**에 둔다.

```
quizImages/<quizId>/<imgId> = "data:image/jpeg;base64,..."   // 문자열 하나
```

**분리가 핵심이다.** 방(`rooms/<code>`)은 참가자 전원이 실시간 구독하고 있어서,
누군가 답을 제출해 점수가 바뀔 때마다 방 데이터 전체가 다시 내려온다. 이미지를 방 안에 넣으면
그때마다 이미지까지 통째로 재전송되어 전송량이 폭발하고 화면도 버벅인다.
`quizImages/`를 따로 두면 참가자는 그 이미지를 **한 번만** 내려받아 캐시한다.

방은 지금처럼 `quizId`를 들고 있으므로(`createRoom`이 이미 저장한다) 참조만으로 이미지를 찾을 수 있다.

## 5. 이미지 넣기

### 왜 Firebase Storage를 쓰지 않는가

2026-09-16 확인 결과, `dracula-818e1` 프로젝트의 Storage는 **결제 계정(Blaze 요금제)을 요구한다.**
무료 요금제(Spark)로는 켤 수 없다. 대신 이미 무료로 쓰고 있는 **Realtime Database에 이미지를 직접 저장**한다.
드래그 앤 드롭 경험은 그대로 유지되고, 콘솔에서 추가로 켜거나 설정할 것이 없다.

### 방식

편집기의 문항 카드에 이미지 영역을 두고, 파일을 **끌어다 놓거나** 눌러서 고른다.

1. `image/*`만 받는다. 원본 20MB 초과는 받기 전에 거부하고 이유를 알려 준다.
2. 브라우저에서 축소·압축한다 — 긴 변 최대 **1280px**, JPEG 품질 0.75,
   투명 배경은 흰색으로 채운다(캔버스로 그린 뒤 `toDataURL('image/jpeg', q)`).
3. **400KB 상한을 맞춘다.** base64 문자열이 400KB를 넘으면 품질을 0.75 → 0.6 → 0.5로 낮춰 다시 인코딩하고,
   그래도 넘으면 긴 변을 1024px → 800px로 줄인다. 끝내 못 맞추면 "이미지가 너무 복잡해요"로 거부한다.
4. `quizImages/<quizId>/<imgId>`에 문자열로 저장하고, 문제에는 `{ id, w, h }`만 넣는다.
5. 저장 중에는 카드에 진행 상태를 표시하고, 실패하면 카드 안에 오류와 `다시 시도` 버튼을 둔다.

압축 후 100~200KB가 일반적이다. 10문항 전부에 이미지를 넣어도 퀴즈 하나가 2MB 안쪽이다.

### 퀴즈 id 확보

지금은 퀴즈를 저장해야 id가 생긴다. 그러면 새 퀴즈에서는 이미지를 넣을 경로가 없다.
편집기를 열 때 id가 없으면 **미리 하나 발급**해 두고(`push(ref('quizzes')).key`),
저장할 때 그 id를 그대로 쓴다. `saveQuiz`는 이미 `quiz.id`가 있으면 그 경로에 쓰므로 수정이 필요 없다.

### 읽기와 캐시

이미지는 문제를 표시할 때 `get(ref('quizImages/<quizId>/<imgId>'))`로 **한 번만** 받아
메모리 `Map`에 캐시한다. 방 데이터 구독(`onValue`)과는 완전히 분리되어 있으므로,
점수가 갱신되어 방이 다시 내려와도 이미지는 재전송되지 않는다.

**미리 받아 두기** — 다음 문제에 이미지가 있으면 대기 화면과 정답 공개 화면에서 미리 받아 둔다.
문제가 시작되자마자 이미지가 떠 있어야 20초 타이머가 공평하다.

### 삭제

이미지를 바꾸거나 지울 때, 문항을 삭제할 때, 퀴즈를 삭제할 때 해당 노드를 지운다
(`set(ref('quizImages/<quizId>/<imgId>'), null)`, 퀴즈 삭제 시에는 `quizImages/<quizId>` 통째로).
실패해도 편집을 막지 않는다.

### 한도

무료 요금제의 Realtime Database는 **저장 1GB, 월 전송 10GB**다.
24명 × 10문항 × 200KB ≈ 48MB가 워크숍 1회분이므로 여유가 크다.
전송량은 Firebase 콘솔의 Realtime Database → 사용량에서 확인할 수 있다.

### 규칙

현재 DB 규칙이 이미 공개(`read/write: true`)라 추가 설정이 필요 없다.
다만 그만큼 누구나 쓸 수 있으므로 12절의 리스크 항목을 함께 본다.

## 6. 문제별 순위

### 기준

**그 문제를 빨리 맞힌 순서.** 정답자만 대상이고, 제한시간(20초)을 넘겨 도착한 답은 제외한다.
순서는 `answeredAt - startedAt`(제출까지 걸린 시간) 오름차순.

이 기준은 점수 체계와 어긋나지 않는다. 점수가 `100 + 속도보너스(최대 100)`이고
x2 배점은 문항 전체에 똑같이 적용되므로, **같은 문제 안에서는 빨리 맞힌 순 = 그 문제에서 많이 받은 순**이
항상 일치한다.

동점(같은 밀리초)은 닉네임 가나다순으로 가른다 — 기존 `rankPlayers`와 같은 규칙.

### 필요한 데이터

이미 저장되고 있다. `rooms/<code>/answers/<문제번호>/<플레이어>` = `{ value, answeredAt }`,
그리고 `rooms/<code>/startedAt`. 새로 쌓을 데이터는 없다.

### 새 순수 함수 (`js/logic.js`)

```js
// 한 문제의 순위 — 정답자만, 빨리 맞힌 순
rankQuestion(question, answersForQ, players, startedAt)
  // → [{ id, nick, elapsedMs, gained }]

// 참가자별 맞힌 개수 — 최종 결과와 CSV용
summarize(questions, answers, players)
  // → { [playerId]: { correct, answered } }
```

둘 다 순수 함수라 기존 테스트 방식(`test/`)으로 검증한다.

### 보이는 곳

- **강사 대형 스크린 · 정답 공개** — 좌우 2단. 왼쪽 `⚡ 이번 문제 빨리 맞힌 순` TOP 5(걸린 시간 표시),
  오른쪽 `누적 순위` TOP 5.
- **교육생 폰 · 정답 공개** — 정답이면 "⚡ 이번 문제 N번째로 맞힘", 오답이면 정답만 알려 준다.
  아래에 누적 순위와 점수.

## 7. 최종 결과 — 세 화면으로 분리

문제는 지금 `admin.html` 한 화면이 강사 노트북이자 대형 스크린이라는 점이다.
전체 순위를 같은 창에 띄우면 프로젝터에도 그대로 나간다. 그래서 화면을 나눈다.

| 보는 사람 | 어디 | 무엇 |
|---|---|---|
| 모두 (프로젝터) | `admin.html` 최종 화면 | 1·2·3등 시상대만. 4위 이하는 나오지 않는다 |
| 강사 | `results.html` (새 창) | 전체 순위 + 맞힌 개수 + CSV 내보내기 |
| 교육생 각자 | `index.html` 최종 화면 | 내 등수 / 총 인원 / 점수 / 맞힌 개수 |

시상대 화면의 `전체 순위 보기` 버튼이 `window.open('results.html?room=<코드>')`로 새 창을 연다.
강사가 노트북 화면과 프로젝터를 확장 디스플레이로 쓰면 교육생에게 보이지 않는다.
(미러링 상태라면 어차피 보이는데, 이건 화면 구성으로 해결할 수 없는 물리적 제약이다.)

`results.html`은 별도 창이므로 관리자 암호를 다시 한 번 묻는다. 방 코드만 있으면
워크숍이 끝난 뒤에도 결과를 다시 열어 볼 수 있다.

### CSV 형식

```
순위,닉네임,점수,맞힌개수,Q1,Q2,...
1,민서,1480,9,O,O,X,...
```

`Blob` + `URL.createObjectURL`로 내려받는다. 파일명은 `<퀴즈제목>_결과.csv`,
한글이 깨지지 않도록 UTF-8 BOM을 붙인다.

## 8. 편집기

- 문항 유형 추가 버튼 3개(`＋ 객관식` / `＋ O/X` / `＋ 단답형`)를 점선 카드로
- 문항 카드는 **접힌 상태가 기본**, 누르면 펼쳐진다. 펼쳐진 카드는 한 번에 하나
- 카드 머리에 번호·유형 배지, 오른쪽에 `↑ ↓ ⧉ 🗑` (위로·아래로·복제·삭제)
- 정답 지정을 라디오 버튼에서 **보기 옆 동그라미 체크**로 — 누르면 민트로 채워진다
- 이미지 영역: 비어 있으면 "이미지를 끌어다 놓으세요", 있으면 썸네일 + `바꾸기` / `🗑`

## 10. 오류 처리

| 상황 | 동작 |
|---|---|
| 이미지 저장 실패 | 문항 카드 안에 이유와 `다시 시도` 버튼. 다른 편집은 계속 가능 |
| 이미지 파일이 너무 큼 / 형식이 아님 | 받기 전에 거부하고 무엇이 문제인지 알려 준다 |
| 압축해도 400KB를 못 맞춤 | "이미지가 너무 복잡해요 — 더 단순한 그림이나 작은 사진을 써 주세요" |
| 참가자 화면에서 이미지 로드 실패 | 이미지 자리를 접고 문제와 보기만 보여 준다. 문제 풀이는 막히지 않는다 |
| 이미지가 아직 도착하지 않음 | `w`/`h`로 잡아 둔 자리에 옅은 회색 placeholder. 도착하면 채워진다 |
| `results.html` 방 코드가 없거나 틀림 | "결과를 찾을 수 없어요" + 코드 다시 입력 |

## 11. 테스트

1. **단위** — 기존 8개 유지 + `rankQuestion`(정답자만 / 시간초과 제외 / 동점 / 빈 응답),
   `summarize`(맞힌 개수) 추가
2. **실기기 E2E** — 실제 Firebase로 2탭 이상: 이미지 문제 만들기 → 방 열기 → QR 입장 →
   이미지 문제 풀기 → 문제별 순위 확인 → 최종 시상대 → 전체 순위 창 → CSV → 개인 폰 결과
3. **폰 확인** — 실제 스마트폰에서 보기 버튼 터치 영역과 이미지 문제 레이아웃

## 12. 리스크

- **DB 전송량** — 이미지가 DB 전송량을 쓴다. 24명 × 10문항 기준 약 50MB로 월 10GB 한도에는 여유가 크지만,
  워크숍을 자주 돌리면 콘솔의 사용량을 한 번씩 확인하는 게 좋다. README에 확인 방법을 적어 둔다.
- **이미지를 방에 넣지 말 것** — 이 설계의 전제다. 나중에 누군가 편의상 `rooms/` 안에 이미지를 복사하면
  참가자 전원이 방 갱신마다 이미지를 다시 받게 되어 전송량이 수십 배로 뛴다. 코드에 주석으로 못 박는다.
- **공개 쓰기 규칙** — DB 규칙이 열려 있어 방 코드를 모르는 사람도 쓸 수 있다.
  워크숍 용도라 감수하되, 자주 쓰게 되면 규칙 강화를 별도 과제로 잡는다.
- **응답 노출** — 참가자가 방 전체를 구독하므로 남의 답도 기술적으로는 보인다.
  이건 지금도 마찬가지이고, 이번 작업으로 나빠지지 않는다. 경쟁용으로 쓸 거면 별도 과제.
